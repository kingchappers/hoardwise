# MCP OAuth sign-in and the AI assistants page Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let a person connect Claude (web, desktop, then phone) to their Hoardwise by pasting its URL and pressing Connect, with sign-in and a "view only" / "view and change" consent screen, on both the AWS and self-hosted deployments (HOA-15), and add the Settings "AI assistants" page that explains how to connect (HOA-13).

**Architecture:** Hoardwise is its own small OAuth 2.1 authorization server. An OAuth connection is a normal Hoardwise access token (`hwr_` / `hww_`, hashed, revocable) with a short life, plus a rotating refresh token, so `/mcp` authentication, scope checks and the Settings tokens list work unchanged. Sign-in and consent happen in the existing SPA (a new `/connect` page), which works in Auth0 and local-login modes alike; the server endpoints are plain JSON handlers in the shared API code. The SDK stays the resource server for `/mcp` only.

**Tech Stack:** TypeScript, the shared `Store` (DynamoDB / SQLite / memory), `node:crypto` (PKCE S256 is a SHA-256 compare, no new dependency), React 19 + Mantine 8, OpenTofu.

**Spec:** `docs/superpowers/specs/2026-10-31-mcp-design.md` (sections "Safety rules", "The official MCP SDK", "Left to the builder"). Plan 1 and the SDK swap are merged (PRs #122, #123).

## Global Constraints

- Never read, log or commit a token, refresh token, authorization code, client secret or setup code. Log ids and outcomes only (SEC-01, AUTH-18).
- PKCE `S256` is required on every authorization. Redirect URIs are matched **exactly** against those registered. Authorization codes live 60 s and are single-use.
- Every unauthenticated route (`register`, `token`, `revoke`, the two discovery documents) does the least work, has a body cap of 8 KiB, a per-address limiter, and an API Gateway route throttle on AWS.
- The issuer is the configured `APP_ORIGIN` (scheme + host + port). It is **never** taken from `Host` or `X-Forwarded-*`. When `APP_ORIGIN` is unset, the OAuth routes answer 404 and `/mcp` sends no discovery hint.
- Token lifetimes: access 3600 s; refresh 90 days, rotated on every use. Scope on the consent screen is `read` (default) or `write`; nothing else.
- Registered-client limits: at most 500 clients per instance, at most 5 redirect URIs each (each at most 2,000 characters), client name clipped to 60 characters, unused registrations expire after 24 hours (at the cap the oldest never-used client is evicted; registration is refused only when every client is in use), used ones 90 days after last use. A person may hold the existing 25-token cap in total.
- A route that tokens must not reach goes in `NON_TOKEN_PATHS`; consent is one (`/api/oauth/authorize`).
- In local-login mode, choosing "view and change" re-asks for the password, as the Settings token form does (`needsPassword` in `src/api/tokens.ts`).
- Copy follows `docs/brand.md` and the skill's calm wording; no flashing or motion; colour never carries meaning alone.
- Conventional commits, controls referenced (AUTH-xx, INFRA-01, IO-01); two trailer lines per the session attribution.

## Review Focus

1. A second person on the same instance (or a stale grant) must not see, use or revoke another person's connection or codes. Test: user B cannot revoke user A's grant through any route; a code issued for A cannot be exchanged into B's token.
2. Registration flood: 1,000 `POST /api/oauth/register` calls from one address stop growing the table at the cap and return 429/503, never an unbounded write.
3. Code and refresh-token replay: a used code, an expired code, a wrong `code_verifier`, a different `redirect_uri`, or a different `client_id` all fail with the same generic `invalid_grant`; presenting an already-rotated refresh token revokes the whole connection.
4. Open-redirect and phishing on `/connect`: an unregistered `redirect_uri` is **never** redirected to (the page shows an error instead); the consent screen shows the client's name as data plus the exact redirect host.
5. Revoking the connection in Settings kills both the access token and the refresh token at once, and the next `/mcp` call is a 401.
